1. Summary

Can we produce the same report from SSAS? Yes for its content, though not by repointing the existing file.

Content Carried over
The 71-KPI catalogue and its four pillars Yes
Hospital, category and period selection Yes
Overview score, pillar scores, section boards, hospital comparison and the owner view Yes

Repointing the handover pbix at SSAS as it stands would break requirements 3 and 4:

  • Configuration lives in the model and the visuals. The handover model is about 258 measures over calculated tables. Its configuration is typed into the model (DATATABLEs) and into roughly 2.5 MB of JavaScript duplicated across 9 custom visuals: KPI list, owners, weights, thresholds, hospital ids and categories.
  • The model breaks SSAS conventions. Our model bans calculated tables (BPA rule HNH_NO_CALCULATED_TABLES).
  • The boards cannot drill through. They use the 2018 "D3JSVisual" (plugin API 1.9), which cannot start a drill-through, a tooltip or a cross-filter.

Recommended approach. It is detailed in section 5.

  • KPIs are computed once a month per branch in dbt, as numerator and denominator. They reuse the corrected bsc view logic already built on gold.
  • All configuration comes from static tables:
    • KPI catalogue, targets, weights, thresholds and owners;
    • hospital categories;
    • manual KPI values.
  • SSAS gets a few small tables, about 12 generic measures, and a perspective Balanced Scorecard.
  • The report is rebuilt over a live connection: a new branded custom visual for the scorecard pages, native visuals for the drill-through pages.
  • Drill-through goes from KPI to a KPI detail page, then to the transaction-level facts already in the model.

What the scorecard actually shows today. Only 45 of the 71 KPIs return a value (section 3.2). The other 26 have no measure, no data, or columns that do not exist on the warehouse the report reads. The rebuild should start with those 45, then add the rest in the groups set out in section 7.

2.2 Report (Hayat_BSC_Full_RS.Report, 10 pages)

Pages:

  • BSC (landing gauge)
  • BSC Overview, plus its Expanded and Ownership variants
  • Financial, Customer, Internal Process, Learning & Growth (section boards)
  • Hospital Comparison
  • Instruction Manual (hidden)

What every page has:

  • Slicers: four synced ones (Hospital View, Category, From month, To month).
  • Navigation: native transparent buttons laid over pills drawn by a D3 header.

How the boards work:

  • Data: every KPI board is a D3JSVisual running 130–385 KB of JavaScript, fed by one table-shaped field well.
  • Scoring is computed in JavaScript, not DAX:
    • variance % = (a − t) / |t|, reversed for lower-is-better KPIs;
    • score = clamp(85 + 0.6 × variance);
    • status: good ≥ 85, warn ≥ 70, bad below that.
  • Pillar and overall scores are weighted means of the unit score:
    • unit score = a/t, t/a, a ceiling rule, or an on-target band;
    • weights come from _V9_WEIGHT_PROFILES (14 profiles × 21 name aliases);
    • pillar weights are Financial 0.30, Customer 0.20, Internal Process 0.35, Learning & Growth 0.15.

What the boards cannot do:

  • Interact with the rest of the report. They create no selection ids and have no context menu, tooltips or URL launch. A click changes state inside the visual only. The overview's "↗ Dashboard" link is a stub (/* drill-through not configured */).
  • Hide KPIs securely on the section pages. The hiding happens in the browser only. The Access Keys tables relate one-way to the pillar tables, so every figure still reaches the browser and is visible through Export data.

6.2 DWH layer: all configuration lives here

Config tables

These are reference tables in ClickHouse default (default.map_bsc_*), and the tables themselves are the source of truth. There is no workbook, no CSV and no loader script (decision D6). The BI manager edits them directly with SQL (decision D7).

Each table is an insert-only change log:

  • Columns: the key, the values, then changed_at DateTime64(3), changed_by String, change_note String and is_deleted UInt8.
  • How a change is made: insert a new row for the key. Nothing is ever updated in place: there are no ALTER … UPDATE mutations.
  • Delete: a row with is_deleted = 1.
  • Current value: the stg_ref__bsc_* view takes the latest row per key (argMax(…, changed_at)) and drops deleted keys.
  • History: every value ever set, who set it and why stays queryable.
  • Undo: insert the previous values again.

The tables are created once, and their first content is generated from the handover project. Both steps are ClickHouse writes and need approval. Section 6.2.1 shows the editing routine.

Table Key Holds
map_bsc_kpi kpi_code kpi_num, name, short label, pillar, objective code, type (Primary / Supporting / Additional), direction (higher / lower / ceiling / on_target / variance), format, chart hint, display order, definition text, is_active, and the composition: numerator metric, denominator metric, multiplier, rollup rule, period rule, target source. Where a KPI has two candidate definitions (Appendix B), both are built as metrics, and switching between them is a change to the composition
map_bsc_objective objective_code Pillar, title, question, order. Pillar weights 0.30 / 0.20 / 0.35 / 0.15
map_bsc_target kpi_code, branch_id (0 = all), year, month (0 = annual) Target value, scale_with_months, basis, note. Replaces TARGETS_INDUSTRY and the DAX constants; seeded from it and from default.bsc_targets
map_bsc_weight Profile (category or branch), kpi_code KPI weight inside the pillar. Replaces _V9_WEIGHT_PROFILES, keyed on category or branch id instead of 21 name aliases
map_bsc_threshold kpi_code (null = default) Score base 85, slope 0.6, good ≥ 85, warn ≥ 70
map_bsc_owner kpi_code, branch_id (null = Corporate) Owner, co-owners. Kept as information for the owner view only, with no security (requirement 2)
map_bsc_hospital_category branch_id Category. Surfaced as a new column BSC Category on gold.dim_branch, so it appears on the SSAS Branch table
map_bsc_manual_value kpi_code, branch_id, year, month Numerator, denominator, value, note, entered by, entered at. Holds group C KPIs and replaces the hand-loaded patient_satisfaction sheet

Metrics. gold.fact_bsc_metric_monthly (metric_code × branch × month × value):

  • It unpivots the existing bsc_vw_* dbt models, so the corrected definitions reconciled in docs/reconciliation_bsc.md are reused, not rewritten.
  • It adds the new group B metrics:
    • final claim rejections;
    • referral volume (already in vw_customer);
    • Saudi headcount;
    • vacancies;
    • average and licensed beds (for activated bed rate);
    • marketing expense from fact_gl_fs_monthly;
    • doctor slots from legacy_capacity_slots.

KPI facts. gold.fact_bsc_kpi_monthly is built by dbt from the metrics and map_bsc_kpi:

  • Columns: numerator, denominator, target_numerator, target_denominator, month_count and data_source.
  • Ratios stay additive: every ratio is stored as its two parts, so a corporate, category or period-range figure is Σnumerator / Σdenominator. The hospitals' rates are never averaged, which matches the scorecard's pooled rule.
  • Stocks (beds, FTE, headcount, AR, assets) are stored with month_count, so averages over a range are correct.

What a change costs:

Change Where Refresh
Target, weight, threshold, owner, category, label, order, direction, format A new version row in the default.map_bsc_* table Nightly dbt + SSAS Daily (or the fast path, with approval)
Swap a KPI's numerator or denominator between existing metrics, change its multiplier or rollup rule map_bsc_kpi Same
A new KPI built from existing metrics A row in map_bsc_kpi, plus targets and weights Same: no SSAS deploy
A new metric (new source logic) dbt SQL in fact_bsc_metric_monthly dbt build + SSAS Daily
A new rollup or period rule (rare) SSAS generic measure SSAS deploy

Tests (on the stg_ref__bsc_* current-value views):

  • Unique keys, accepted values, and foreign keys from every config table to map_bsc_kpi.
  • Every metric named in a composition exists in fact_bsc_metric_monthly.
  • Every active KPI has a target for each budgeted branch (warn).
  • Thresholds are ordered, and manual values exist only for manual KPIs.
  • One row per KPI × branch × month.

A bad edit can't reach the report. If an edit fails a test, the nightly tag:hnh build fails. The SSAS gate stays closed, and the report keeps yesterday's figures. The BI manager can also run dbt test --select stg_ref__bsc_* straight after an edit.

-- Change Days in AR target for 2027 (all hospitals)
INSERT INTO default.map_bsc_target

VALUES ('FIN_DAYS_IN_AR', 0, 2027, 0, 170, 0, 'Board 2027', now64(3), 'bi_manager', 'FY2027 target approved', 0);

-- See the history of a key

The same pattern covers the other tables: a weight, an owner, a hospital's category, a monthly manual value (HAI, falls, training, …), or a KPI's composition. docs/bsc_config.md will list every table, its columns and an example.

Tables. All are small, single-partition tables refreshed in full by process.ps1 -Mode Daily:

Generic measures. About 12, in folder Balanced Scorecard\…:

Group Measures
Values BSC Actual, BSC Target, BSC Variance %
Scoring BSC Score, BSC Status (icon or colour code), BSC Unit Score
Pillar and overall BSC Pillar Score, BSC Overall Score, BSC Hit Rate

How they work:

  • Rules come from data. Each reads its rollup, period and direction rule from BSC KPI columns through a small SWITCH of rule types, not of KPIs. Adding a KPI never touches DAX.
  • Thresholds come from data. Scores read map_bsc_threshold values carried on BSC KPI.
  • Formatting is per KPI. The value is shown in each KPI's own format (%, SAR, days, minutes) through a dynamic format string. Check that SQL Server 2025 AS honours measure format-string expressions in Power BI Report Server visuals; if not, use a formatted-text measure for display.
  • Model conventions apply:
    • KPI Values relates only to Branch, Date and BSC KPI, so the measure_guards.py guards (P41) apply;
    • snapshot handling is not needed, because stocks carry month_count;
    • each measure gets checks in ssas/tests/measures/balanced_scorecard.json against gold.fact_bsc_kpi_monthly.

Perspective Balanced Scorecard:

  • The BSC tables, Branch and Date, Time Calculation;
  • the detail facts used by the drill-through pages (section 6.5);
  • configured through PERSPECTIVES / PERSPECTIVE_MEASURE_DOMAINS in model_config.py.

Who uses it (decision D4). The scorecard is for top management only:

  • Report access: the BI manager grants it through Power BI Report Server folder permissions on the scorecard folder.
  • Data rules: the model keeps its existing rules, unchanged.
  • Excel and other report tools: the perspective is a view, not a security boundary. Any HNH_BI_Users member who connects to the model with Excel can read the BSC tables, still filtered to their own branches. This is acceptable because the scorecard shows only branch-month aggregates of data those users can already see.

Security. HNH Readers is unchanged:

  • Branch filter. It flows to BSC KPI Values through Branch. A user limited to Abha sees Abha only.
  • "Corporate". It means "all hospitals the user may see", and excludes Head Office through Is Hospital.
  • What is dropped:
    • KPI-owner security (the Viewer Access role, the {"*","Full"} fallback, the client-side tile hiding);
    • the e-mail logins, which do not work on this workgroup server anyway (USERPRINCIPALNAME() returns HNHANALYTICSSRV\user).

6.6 Benefits and drawbacks of option B

Benefits

  • One place for configuration. One catalogue drives every page, the scoring and the drill paths. Target, weight, threshold, owner, category and most formula changes are row edits in DWH tables, with no SSAS deploy and no JavaScript editing. This replaces the 15-step change in Notes/06.
  • Correct numbers. It reuses the reconciled bsc logic on gold: Oasis + Fusion GL by cutover, and corrected definitions. That fixes the post-Fusion finance gap and the blank Learning & Growth KPIs.
  • Real drill-through. The new visual opens Power BI's context menu, tooltips and cross-filtering, so drill-through works, from KPI to hospital and month, then to transaction lines.
  • Consistent security. It uses the HNH Readers rules, which close the open *=Full fallback and the browser-only tile hiding.
  • Less to maintain:
    • about 12 measures instead of 258;
    • no calculated tables;
    • no ODBC refresh or chDWH DSN for the report (it connects live);
    • about 2.5 MB of duplicated JavaScript removed.
  • Testable. dbt tests, loader validation, and SSAS measure-against-SQL checks.
  • Group C KPIs get a controlled entry path. Manual values carry an audit trail.

Drawbacks

  • KPIs are pre-aggregated by branch × month. A KPI cannot be sliced by department, payer or doctor; only its detail pages can. Option C would allow that, at the cost of formulas living in SSAS.
  • Two definitions can coexist. For example, Claim Rejection Rate % in SSAS and KPI 33 in the scorecard use different denominators (4.1). Users comparing reports will see differences. Mitigations:
    • label the definition on the KPI Detail page;
    • list the differences;
    • converge one definition at a time.
  • We own a custom visual.
    • The HNH Balanced Scorecard visual is TypeScript code that the BI team must maintain.
    • Each Power BI Report Server upgrade must be checked against the visual's API version.
    • It is a private visual (not certified), so it is imported into the report file.
    • It replaces about 2.5 MB of copied JavaScript with one versioned package that reads its configuration from data.
  • Data is a day old, not near real time. Changes appear after the nightly dbt build and process.ps1 -Mode Daily. Today the report re-queries live views at each refresh. The fast path (-Force) needs approval each time.
  • Branch security only. Pre-aggregated rows have no staff or pay key, so specialty and pay restrictions do not narrow scorecard values. This is acceptable because report access is limited to top management (decision D4). Pay-derived KPIs (for example cost per fire) show branch totals.
  • Manual KPIs need a monthly routine. The BI manager owns it, and every entry is a ClickHouse insert.
  • Edits are SQL inserts. That is fast for the BI manager, but a mistake in a key is only caught by the dbt tests (section 6.2). There is no form with validation.
  • Numbers move. They come from the new server and corrected definitions, so 2025–2026 values differ from the current report, mainly finance after cutover. docs/reconciliation_bsc.md explains the differences.
  • Some changes still need SSAS. A new rule type, a new detail family page, or adding GL FS Monthly for Oasis GL drill-through each need an SSAS deploy (with approval).

8. Path to option C later

Option B does not block option C. When a KPI needs slicing by department, payer or doctor:

  1. Write its SSAS measure over the facts.
  2. Add a measure check that it equals fact_bsc_kpi_monthly at branch × month.
  3. Set map_bsc_kpi.ssas_measure so that the KPI Detail page shows the sliceable version.

Revenue, volumes, BOR, ALOS, readmissions and RCM KPIs are the natural first candidates, because their SSAS measures exist already (4.1).
